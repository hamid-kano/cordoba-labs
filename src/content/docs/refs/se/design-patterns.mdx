<Aside type="tip" title="الفكرة ببساطة">
الطبّاخ لا يخترع طريقة جديدة لصنع العجين كل يوم. هناك **وصفات** مجرّبة يعرفها كل الطبّاخين: عجين الخبز، وعجين الكعك. وفي البرمجة أيضاً مشكلات تتكرر في كل مشروع، ولها **وصفات** مجرّبة اسمها **أنماط التصميم**.
</Aside>

## ماذا ستتعلم؟

- ما هو **نمط التصميم**، ولماذا لا نخترع الحل من جديد.
- نمط **MVC** الذي تُبنى عليه أغلب المواقع والتطبيقات.
- ثلاثة أنماط مشهورة: **المراقب** و**الوحيد** و**المصنع**.
- مبادئ **SOLID** الخمسة لكتابة كود يسهل تعديله.

## ما هو نمط التصميم؟

<Concept term="نمط التصميم" en="Design Pattern">

**حل مجرّب** لمشكلة تصميم تتكرر كثيراً، له اسم معروف. ليس كوداً جاهزاً تنسخه، بل **فكرة** تطبّقها بلغتك. مثل وصفة الطبخ: تعطيك الخطوات، وأنت تطبخ بمطبخك.

**لماذا نستخدمه؟** لأنه جُرّب آلاف المرات فنعرف أنه يعمل. ولأنه **لغة مشتركة**: عندما يقول مبرمج لزميله «استخدم المراقب هنا»، يفهمه فوراً دون شرح طويل.

**أين يُستخدم؟** في كل مكان: أُطر المواقع مثل <Term t="Laravel" en="Laravel" def="إطار عمل مشهور لبناء المواقع بلغة PHP، مبني على نمط MVC." /> و <Term t="Django" en="Django" def="إطار عمل لبناء المواقع بلغة Python، مبني على فكرة قريبة من MVC." />، وتطبيقات الهاتف، والألعاب. واشتهرت الأنماط بكتاب عصابة الأربعة <Term t="GoF" en="Gang of Four" def="لقب المؤلفين الأربعة لكتاب «أنماط التصميم» عام 1994، وفيه 23 نمطاً ما زالت تُستخدم حتى اليوم." /> عام 1994، وفيه 23 نمطاً.

</Concept>

## نمط MVC: افصل البيانات عن الشكل

أشهر نمط على الإطلاق. يقسم البرنامج ثلاثة أجزاء، وتُسمّى معاً <Term t="MVC" en="Model–View–Controller" def="نمط يقسم البرنامج إلى: نموذج يحفظ البيانات، وعرض يرسمها، ومتحكم يستقبل أفعال المستخدم ويغيّر النموذج." />:

| الجزء | وظيفته | في المطعم |
| --- | --- | --- |
| **النموذج** | يحفظ البيانات وقواعدها | المطبخ والمخزن |
| **العرض** | يرسم البيانات للمستخدم | الطبق الذي يصلك |
| **المتحكم** | يستقبل أفعال المستخدم ويطلب من النموذج التغيير | النادل يأخذ طلبك |

جرّب المكيّف التالي: له **عرضان** (شاشة المكيّف وتطبيق الهاتف)، ونموذج واحد:

<MvcLab />

1. اضغط «＋ درجة» عدة مرات، وتابع الترتيب في القائمة: المتحكم ← النموذج ← العرضان.
2. فعّل «اكسر النمط» واضغط مرة أخرى. **ماذا يجب أن ترى؟** الشاشة تغيّرت وحدها، والهاتف بقي على الرقم القديم.

**الدرس:** عندما تحفظ البيانات في مكان واحد فقط (النموذج)، تتفق كل العروض دائماً. ونستطيع أن نضيف عرضاً ثالثاً (ساعة ذكية مثلاً) دون أن نلمس النموذج.

## نمط المراقب: أخبرني عندما يتغيّر شيء

مشكلة: عدة أجزاء تريد أن تعرف عندما يتغيّر شيء ما. هل يسأل كل جزء كل دقيقة «هل من جديد؟»، أم **يُخبَر** وحده؟ الحل هو <Term t="نمط المراقب" en="Observer Pattern" def="نمط يشترك فيه عدة مراقبين عند صاحب الخبر، فإذا تغيّر شيء يخبرهم كلهم تلقائياً، دون أن يسألوا." />، وهو بالضبط زر «اشترك» وجرس الإشعارات:

<ObserverLab />

**ماذا يجب أن ترى؟** الإشعار يصل فقط لمن ضغط «اشترك». وفي المقارنة: بدون المراقب يُرسل عشرات الرسائل الضائعة، وبالمراقب رسالة واحدة لكل مشترك.

ولاحظ أن المكيّف في الفقرة السابقة يستخدم المراقب أيضاً: النموذج يخبر العرضين عندما تتغيّر الحرارة.

## نمط الوحيد: نسخة واحدة فقط

بعض الأشياء يجب أن يكون منها **نسخة واحدة** في البرنامج كله: طابور الطابعة، وملف الإعدادات، والاتصال بقاعدة البيانات. وهذا هو <Term t="نمط الوحيد" en="Singleton Pattern" def="نمط يضمن أن للصنف نسخة واحدة فقط في البرنامج كله، وكل من يطلبه يحصل على النسخة نفسها." />:

<SingletonLab />

```java
class PrintQueue {
    private static PrintQueue instance;   // النسخة الوحيدة
    private PrintQueue() { }              // ممنوع new من الخارج

    static PrintQueue getInstance() {
        if (instance == null) instance = new PrintQueue();
        return instance;                  // الكل يأخذ النسخة نفسها
    }
}
```

<Aside type="caution" title="لا تكثر منه">
الوحيد يشبه «متغيراً عاماً» يستطيع كل أحد تغييره، وهذا يصعّب الاختبار. استخدمه فقط عندما تكون النسخة الواحدة **ضرورة حقيقية**.
</Aside>

## نمط المصنع: دع غيرك يقرر ماذا يُصنع

تطبيق توصيل فيه أنواع مركبات: دراجة، وسيارة، وشاحنة. لو كتبنا `new Car()` في كل مكان، فإضافة «طائرة مسيّرة» غداً تعني البحث عن كل تلك الأماكن. والحل هو <Term t="نمط المصنع" en="Factory Pattern" def="نمط نضع فيه قرار «أي نوع ننشئ» في مكان واحد (المصنع)، فيطلب باقي البرنامج ما يريد دون أن يعرف تفاصيل الإنشاء." />: مكان واحد يقرر:

```java
class VehicleFactory {
    static Vehicle create(double weightKg) {
        if (weightKg < 5)   return new Bike();
        if (weightKg < 500) return new Car();
        return new Truck();
    }
}

// في باقي البرنامج: لا يهمنا النوع
Vehicle v = VehicleFactory.create(order.weight);
v.deliver(order);
```

لإضافة «طائرة مسيّرة» نعدّل **المصنع فقط**، وباقي البرنامج لا يتغيّر.

## مبادئ SOLID

خمسة مبادئ، كل حرف من كلمة <Term t="SOLID" en="SRP, OCP, LSP, ISP, DIP" def="الحروف الأولى لخمسة مبادئ في تصميم الأصناف تجعل الكود سهل التعديل والاختبار، جمعها المهندس روبرت مارتن." /> هو أول حرف من مبدأ. الهدف واحد: **كود يسهل تعديله دون أن ينكسر**.

| الحرف | المبدأ | ببساطة |
| --- | --- | --- |
| **S** | المسؤولية الواحدة | لكل صنف وظيفة واحدة، وسبب واحد للتغيير |
| **O** | مفتوح للإضافة، مغلق للتعديل | نضيف ميزة جديدة بكود جديد، لا بتعديل كود يعمل |
| **L** | الاستبدال | الابن يجب أن يعمل في كل مكان يعمل فيه الأب |
| **I** | فصل الواجهات | لا تجبر صنفاً على عمليات لا يحتاجها |
| **D** | الاعتماد على الفكرة لا التفاصيل | اعتمد على «طريقة دفع» عامة، لا على «فيزا» بالتحديد |

أهم مبدأين بمثال «قبل وبعد»:

<Tabs>
<TabItem label="S: المسؤولية الواحدة">

**قبل:** صنف واحد يحسب الفاتورة، ويطبعها، ويرسلها بالبريد. فإذا تغيّر شكل الطباعة أو خادم البريد، نعدّل صنف الفاتورة.

```java
class Invoice {
    double total() { ... }
    void print() { ... }      // طباعة
    void sendEmail() { ... }  // بريد
}
```

**بعد:** كل وظيفة في صنف خاص بها.

```java
class Invoice        { double total() { ... } }
class InvoicePrinter { void print(Invoice i) { ... } }
class InvoiceMailer  { void send(Invoice i) { ... } }
```

</TabItem>
<TabItem label="O: مفتوح ومغلق">

**قبل:** كل طريقة دفع جديدة تعني تعديل هذه الدالة التي تعمل جيداً، وقد نكسرها.

```java
double fee(String type, double amount) {
    if (type.equals("card"))   return amount * 0.02;
    if (type.equals("wallet")) return amount * 0.01;
    // طريقة جديدة؟ نعدّل هنا...
}
```

**بعد:** كل طريقة صنف مستقل. لإضافة طريقة جديدة نكتب صنفاً جديداً، ولا نلمس الكود القديم.

```java
interface Payment { double fee(double amount); }
class Card   implements Payment { public double fee(double a) { return a * 0.02; } }
class Wallet implements Payment { public double fee(double a) { return a * 0.01; } }
class Cash   implements Payment { public double fee(double a) { return 0; } }  // جديد
```

</TabItem>
</Tabs>

## الخلاصة

- **نمط التصميم** حل مجرّب لمشكلة متكررة، ولغة مشتركة بين المبرمجين.
- **MVC**: نموذج للبيانات، وعرض للشكل، ومتحكم للأفعال. والبيانات في مكان واحد.
- **المراقب**: من يهتم يشترك، وصاحب الخبر يخبر الجميع عند التغيير.
- **الوحيد**: نسخة واحدة فقط، ولا نكثر منه.
- **المصنع**: مكان واحد يقرر أي نوع ننشئ.
- **SOLID**: خمسة مبادئ هدفها كود يسهل تعديله دون أن ينكسر.

## أسئلة المراجعة

<details class="answer">
<summary>ما الفرق بين نمط التصميم ومكتبة جاهزة؟</summary>

المكتبة كود جاهز تستدعيه. أما النمط ففكرة حل تكتب أنت كودها بلغتك وبما يناسب مشروعك.
</details>

<details class="answer">
<summary>في MVC، لماذا لا يغيّر العرض البيانات مباشرة؟</summary>

لأن البيانات تصبح في أكثر من مكان فتختلف، كما رأيت عند «كسر النمط». كل تغيير يمر عبر المتحكم إلى النموذج، والنموذج يخبر كل العروض.
</details>

<details class="answer">
<summary>لماذا المراقب أفضل من أن يسأل كل جزء كل دقيقة؟</summary>

لأن السؤال المتكرر يرسل رسائل كثيرة جوابها «لا جديد»، ويتأخر في معرفة التغيير. والمراقب يرسل رسالة واحدة لكل مهتم، في لحظة التغيير نفسها.
</details>

<details class="answer">
<summary>كيف يمنع نمط الوحيد إنشاء نسخة ثانية؟</summary>

يجعل الباني خاصاً فلا يُستدعى `new` من الخارج، ويعطي دالة واحدة تُرجع النسخة الموجودة، أو تنشئها مرة واحدة فقط إذا لم توجد.
</details>

<details class="answer">
<summary>اشرح مبدأ «مفتوح للإضافة، مغلق للتعديل» بمثال.</summary>

لإضافة طريقة دفع جديدة نكتب صنفاً جديداً يطبّق واجهة «طريقة دفع»، بدل أن نضيف شرطاً جديداً داخل دالة قديمة تعمل. فلا نخاطر بكسر ما يعمل.
</details>
