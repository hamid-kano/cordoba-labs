<Aside type="tip" title="الفكرة ببساطة">
السيارة لا تنتهي قصتها عند شرائها: تغيّر الزيت، وتصلح الإطار، وتضيف شاشة، وتجهّزها للشتاء. والبرامج كذلك، بل أكثر: أغلب عمر البرنامج وكلفته تأتي **بعد** التسليم، في **الصيانة**.
</Aside>

## ماذا ستتعلم؟

- ما هي **الجودة** في البرامج.
- أنواع **الصيانة** الأربعة.
- ما هو **الدَّين التقني**، ولماذا يبطئ الفريق.
- ما هي **إعادة الهيكلة**.

## الجودة

البرنامج الجيد ليس الذي «يعمل» فقط، بل الذي:

| الصفة | المعنى |
| --- | --- |
| **صحيح** | يفعل ما في المتطلبات |
| **موثوق** | لا يتعطل كثيراً، وإذا تعطل لا يضيّع البيانات |
| **سريع** | يستجيب في وقت مقبول |
| **سهل الاستخدام** | يتعلّمه المستخدم بسرعة |
| **سهل الصيانة** | يستطيع مبرمج آخر أن يفهمه ويعدّله |

والصفة الأخيرة لا يراها الزبون، لكنها **أغلى** صفة على المدى الطويل.

## الصيانة

<Concept term="صيانة البرمجيات" en="Software Maintenance">

كل تعديل على البرنامج **بعد** تسليمه: إصلاح خطأ، أو تحديث، أو إضافة ميزة. وتقول الدراسات إن الصيانة تأخذ في الغالب **أكثر من نصف** كلفة البرنامج طوال عمره.

**لماذا لا ينتهي البرنامج؟** لأن العالم حوله يتغيّر: أنظمة تشغيل جديدة، وقوانين جديدة، وزبائن يريدون المزيد.

</Concept>

| النوع | السبب | مثال من السيارة |
| --- | --- | --- |
| **تصحيحية** | إصلاح خطأ | تصليح الفرامل |
| **تكيّفية** | البيئة تغيّرت | تبديل الإطارات للشتاء |
| **تحسينية** | ميزة جديدة أو تحسين | إضافة شاشة |
| **وقائية** | منع مشكلة قبل أن تقع | تغيير الزيت في موعده |

## الدَّين التقني

<Concept term="الدَّين التقني" en="Technical Debt">

عندما نكتب كوداً **سريعاً وفوضوياً** لننتهي الآن، فكأننا **نستدين** وقتاً من المستقبل. وكما في الدَّين الحقيقي، ندفع **فائدة**: كل تعديل لاحق يصبح أبطأ وأصعب، حتى نسدّ الدَّين بتنظيف الكود.

**هل هو سيئ دائماً؟** لا. أحياناً نستدين عن قصد (لنلحق موعداً مهماً)، لكن بشرط أن **نسدّ** الدَّين بعدها.

</Concept>

**جرّب هذه الخطط واحدة بعد الأخرى:** «سريع» في كل الدورات، ثم «نظيف» في كل الدورات، ثم «سريع» مرتين ثم «تنظيف» مرة ثم «نظيف». أيّها الأفضل؟ ولماذا لا يكفي «السريع» حتى في المدى القصير؟

## إعادة الهيكلة: قبل وبعد

الطريقة لسدّ الدَّين التقني اسمها <Term t="إعادة الهيكلة" en="Refactoring" def="تحسين ترتيب الكود ووضوحه دون أن يتغير ما يفعله. مثل ترتيب الخزانة: الملابس نفسها، لكنك تجد ما تريد بسرعة." />: نحسّن الكود **دون أن يتغير ما يفعله**. قارن بين النسختين، فهما تحسبان الشيء نفسه تماماً:

<Tabs>
<TabItem label="قبل">

```js
function f(a, b, c) {
  if (c == 1) return a * b * 0.9;
  if (c == 2) return a * b * 0.8;
  return a * b;
}
```

ماذا تعني `a` و `b` و `c`؟ ولماذا `0.9`؟ لا أحد يعرف إلا من كتبها، وربما نسي هو أيضاً.

</TabItem>
<TabItem label="بعد">

```js
const DISCOUNT = { student: 0.10, teacher: 0.20 };

function price(unitPrice, quantity, customer) {
  const total = unitPrice * quantity;
  const discount = DISCOUNT[customer] ?? 0;
  return total * (1 - discount);
}
```

أسماء واضحة، والخصومات في مكان واحد. فإذا أردنا خصماً جديداً، نضيف سطراً واحداً فقط.

</TabItem>
</Tabs>

## الخلاصة

- الجودة ليست «يعمل» فقط: الموثوقية والسرعة وسهولة الاستخدام و**سهولة الصيانة**.
- الصيانة أربعة أنواع: **تصحيحية، وتكيّفية، وتحسينية، ووقائية**، وهي أغلب كلفة البرنامج.
- **الدَّين التقني**: الاستعجال اليوم يبطئك غداً، فسدّ الدَّين قبل أن تكبر فائدته.
- **إعادة الهيكلة**: تحسين الكود دون تغيير ما يفعله.

## أسئلة المراجعة

<details class="answer">
<summary>لماذا تكون الصيانة أغلى من بناء البرنامج غالباً؟</summary>

لأن البرنامج يعيش سنوات بعد تسليمه، وفي كل هذه السنوات نصلح ونضيف ونتكيّف مع التغييرات. أما البناء فيأخذ أشهراً فقط.
</details>

<details class="answer">
<summary>ما الفرق بين الصيانة التصحيحية والوقائية؟</summary>

التصحيحية تُصلح خطأً **وقع** فعلاً، والوقائية تمنع خطأً **قبل** أن يقع، مثل تنظيم كود معقد.
</details>

<details class="answer">
<summary>هل تغيّر إعادة الهيكلة ما يفعله البرنامج؟</summary>

**لا**. هي تحسّن ترتيب الكود ووضوحه فقط، ويبقى الناتج كما هو. ولهذا نشغّل الاختبارات قبلها وبعدها لنتأكد.
</details>
