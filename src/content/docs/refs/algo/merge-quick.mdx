## ماذا ستتعلم؟

- فكرة **فرّق تسد** بخطواتها الثلاث.
- **الترتيب بالدمج**: لماذا هو $O(n \log n)$ دائماً، وما ثمنه.
- **الترتيب السريع**: التقسيم حول محور، ولماذا هو الأسرع عملياً، ومتى يصبح بطيئاً جداً.
- لماذا لا يمكن لأي ترتيب بالمقارنة أن يكون أسرع من $n \log n$.
- **الترتيب بالعدّ**: كيف نكسر هذا الحاجز.
- ماذا تستخدم Python و C++ فعلاً.

## فرّق تسد

<Concept term="فرّق تسد" en="Divide and Conquer">

أسلوب لتصميم الخوارزميات بثلاث خطوات: **قسّم** المسألة إلى مسائل أصغر من النوع نفسه، و**حُلّ** كل واحدة (غالباً بالعودية)، ثم **اجمع** الحلول في حل واحد. مثل جيش يهزم جيشاً كبيراً بتقسيمه إلى مجموعات صغيرة.

**لماذا نستخدمه؟** لأن حل مسألتين بحجم $\frac{n}{2}$ ثم جمعهما أرخص بكثير من حل مسألة بحجم $n$ مباشرة، إذا كان العمل ينمو أسرع من n. فـ $2 \times (\frac{n}{2})^2 = \frac{n^2}{2}$، والتقسيم المتكرر يوصلنا إلى $n \log n$.

**أين يُستخدم؟** في أسرع خوارزميات الترتيب، والبحث الثنائي، وضرب الأعداد الضخمة، وتحويل فورييه السريع الذي يعالج الصوت والصورة في كل هاتف.

</Concept>

## الترتيب بالدمج

الفكرة كلها في ثلاثة أسطر:

1. **قسّم** القائمة إلى نصفين.
2. **رتّب** كل نصف بالطريقة نفسها (عودياً). والقائمة ذات العنصر الواحد مرتبة أصلاً: هذه الحالة الأساسية.
3. **ادمج** النصفين المرتبين.

والسحر كله في الدمج: لدمج `[1, 2, 5, 8]` و `[3, 4, 7, 9]` ننظر إلى **أول** عنصر في كل منهما فقط، ونأخذ الأصغر، ونكرر. لا نحتاج أبداً أن ننظر إلى الخلف.

<MergeTree />

**ماذا يجب أن ترى؟**

1. في البداية تنقسم القائمة إلى نصفين، ثم أرباع، ثم عناصر منفردة: **3 مستويات** فقط لثمانية عناصر، لأن $\log_2 8 = 3$.
2. ثم يبدأ الدمج من الأسفل: كل زوج يصبح مرتباً (أخضر)، ثم كل أربعة، ثم الثمانية. والمجموع **17 مقارنة**.
3. جرّب «مرتب أصلاً» و«معكوس»: عدد المقارنات يتغيّر قليلاً، لكن **الشجرة نفسها لا تتغيّر أبداً**. لذلك الدمج $O(n \log n)$ في **كل** الحالات.

<TabItem label="Python">

```python
def merge_sort(a):
    if len(a) <= 1:                  # base case
        return a
    mid = len(a) // 2
    left = merge_sort(a[:mid])       # divide and conquer
    right = merge_sort(a[mid:])
    return merge(left, right)        # combine

def merge(left, right):
    out, i, j = [], 0, 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:      # <= keeps it stable
            out.append(left[i]); i += 1
        else:
            out.append(right[j]); j += 1
    out.extend(left[i:])             # one side may have leftovers
    out.extend(right[j:])
    return out

print(merge_sort([5, 2, 8, 1, 9, 3, 7, 4]))
```

</TabItem>

```cpp
void mergeSort(vector<int>& a, int lo, int hi) {   // sorts a[lo..hi)
    if (hi - lo <= 1) return;
    int mid = (lo + hi) / 2;
    mergeSort(a, lo, mid);
    mergeSort(a, mid, hi);
    vector<int> out;
    int i = lo, j = mid;
    while (i < mid && j < hi)
        out.push_back(a[i] <= a[j] ? a[i++] : a[j++]);
    while (i < mid) out.push_back(a[i++]);
    while (j < hi)  out.push_back(a[j++]);
    copy(out.begin(), out.end(), a.begin() + lo);
}
```

### لماذا n log n؟

انظر إلى الشجرة: في **كل مستوى** ندمج كل العناصر مرة واحدة، أي قرابة $n$ عملية. وعدد المستويات $\log_2 n$. فالمجموع:

$$
T(n) = 2\,T\!\left(\tfrac{n}{2}\right) + n \quad\Longrightarrow\quad T(n) = O(n \log n)
$$

مع مليون عنصر: $n^2$ يعني تريليون عملية، أما $n \log n$ فقرابة 20 مليوناً. **أسرع بخمسين ألف مرة**.

**الثمن:** الدمج يحتاج قائمة إضافية بحجم n، أي ذاكرة $O(n)$. فهو **ليس** في المكان. لكنه **ثابت**، لأننا نأخذ من اليسار عند التساوي (`<=`).

## الترتيب السريع

<Term t="الترتيب السريع" en="Quicksort" def="ترتيب يختار عنصراً اسمه المحور، ويضع كل الأصغر منه في يساره وكل الأكبر في يمينه، ثم يرتّب الجهتين بالطريقة نفسها." /> يعكس الفكرة: بدل أن يقسم بسهولة ثم يتعب في الدمج، **يتعب في التقسيم** فلا يحتاج دمجاً أبداً.

1. اختر عنصراً اسمه <Term t="المحور" en="Pivot" def="العنصر الذي يختاره الترتيب السريع ليقسم القائمة حوله: الأصغر منه يساراً والأكبر يميناً." />.
2. **قسّم**: ضع كل ما هو أصغر منه في اليسار، وكل ما هو أكبر في اليمين. الآن المحور **في مكانه النهائي**!
3. رتّب اليسار واليمين بالطريقة نفسها. ولا حاجة لأي دمج، فكل شيء في مكانه.

<QuickLab />

**ماذا يجب أن ترى؟**

1. مع «عشوائي (8)» والمحور الأخير: المحور البنفسجي (4) يجد مكانه بعد أول جولة، فيصبح أخضر، ثم يتكرر الأمر في كل جهة. المجموع **16 مقارنة**، والعمق **5**.
2. اختر «مرتب (16)» والمحور **الأخير**، واضغط «النتيجة»: **120 مقارنة**، والعمق **16**! في كل مرة يكون المحور أكبر عنصر، فلا يبقى شيء في يمينه، والجزء يصغر بعنصر واحد فقط.
3. غيّر المحور إلى **الأوسط** مع القائمة نفسها: **38 مقارنة** فقط، والعمق 5.
4. جرّب **عشوائي** عدة مرات: الرقم يتغيّر قليلاً كل مرة، لكنه يبقى قريباً من الأفضل.

```python
import random

def quick_sort(a, lo=0, hi=None):
    if hi is None:
        hi = len(a) - 1
    if lo >= hi:
        return
    p = random.randint(lo, hi)            # random pivot
    a[p], a[hi] = a[hi], a[p]             # move it to the end
    i = lo                                # a[lo..i) < pivot
    for j in range(lo, hi):
        if a[j] < a[hi]:
            a[i], a[j] = a[j], a[i]
            i += 1
    a[i], a[hi] = a[hi], a[i]             # pivot in its final place
    quick_sort(a, lo, i - 1)
    quick_sort(a, i + 1, hi)
```

</TabItem>

```cpp
#include <random>
mt19937 rng(random_device{}());

void quickSort(vector<int>& a, int lo, int hi) {
    if (lo >= hi) return;
    int p = uniform_int_distribution<int>(lo, hi)(rng);
    swap(a[p], a[hi]);
    int i = lo;                           // a[lo..i) < pivot
    for (int j = lo; j < hi; j++)
        if (a[j] < a[hi]) swap(a[i++], a[j]);
    swap(a[i], a[hi]);
    quickSort(a, lo, i - 1);
    quickSort(a, i + 1, hi);
}
```

هذه طريقة التقسيم اسمها <Term t="تقسيم Lomuto" en="Lomuto Partition" def="طريقة بسيطة لتقسيم الترتيب السريع: نمرّ على العناصر، وكل عنصر أصغر من المحور ننقله إلى منطقة في بداية الجزء." />، وهي الأبسط للفهم. وهناك طريقة أسرع قليلاً اسمها **تقسيم Hoare**، بمؤشرين يتحركان من الطرفين نحو الوسط.

### أفضل حالة وأسوأ حالة

| الحالة | ماذا يحدث | التعقيد |
| --- | --- | --- |
| **أفضل حالة** | المحور يقسم الجزء إلى نصفين متساويين | $O(n \log n)$ |
| **الحالة المتوسطة** | تقسيم «جيد بما يكفي» في معظم المرات | $O(n \log n)$ |
| **أسوأ حالة** | المحور دائماً أكبر أو أصغر عنصر | $O(n^2)$ |

**كيف نتجنّب أسوأ حالة؟** نختار المحور **عشوائياً**، أو نأخذ **وسيط ثلاثة**: الأول والأوسط والأخير، ونختار الأوسط بينها. عندها يصبح احتمال أسوأ حالة ضئيلاً جداً، مهما كانت المدخلات.

<Aside type="caution" title="هجوم حقيقي">
بعض المواقع كانت تستخدم ترتيباً سريعاً بمحور ثابت. فاكتشف المهاجمون أنهم يستطيعون إرسال مدخلات مرتبة بطريقة خاصة، تجعل الخادم يقع في أسوأ حالة $O(n^2)$ ويتوقف عن العمل. لذلك تستخدم المكتبات الحديثة محوراً عشوائياً أو حمايات أخرى.
</Aside>

### لماذا السريع أسرع عملياً من الدمج؟

كلاهما $O(n \log n)$ في المتوسط، لكن السريع:

- يرتّب **في المكان**: لا يحتاج قائمة إضافية، بل ذاكرة $O(\log n)$ لمكدس العودية فقط.
- يمرّ على الذاكرة **بالترتيب** (من اليسار إلى اليمين)، وهذا ما يحبه المعالج، فيستفيد من <Term t="الذاكرة المخبئية" en="Cache" def="ذاكرة صغيرة سريعة جداً داخل المعالج، تحفظ البيانات القريبة مما استُخدم مؤخراً، فيكون الوصول إليها أسرع بكثير من الذاكرة الرئيسية." />.
- ثوابته صغيرة: عمليات قليلة في كل خطوة.

لكنه **غير ثابت**، وأسوأ حالته $O(n^2)$. أما الدمج فثابت ومضمون.

## هل يمكن أسرع من n log n؟

**ليس بالمقارنات.** فكّر في الأمر هكذا: لثمانية عناصر هناك $8! = 40{,}320$ ترتيباً ممكناً، والخوارزمية يجب أن تعرف أيها هو الصحيح. وكل مقارنة سؤال جوابه نعم أو لا، فتقسم الاحتمالات إلى نصفين في أحسن الأحوال. إذن نحتاج على الأقل هذا العدد من المقارنات:

$$
\log_2 (n!) \approx n \log_2 n
$$

لثمانية عناصر: $\log_2 40320 \approx 15.3$، أي **16 مقارنة على الأقل** في أسوأ حالة. والدمج احتاج 17. قريب جداً من الحد! هذا الحد اسمه <Term t="الحد الأدنى للترتيب" en="Comparison Sort Lower Bound" def="إثبات أن أي خوارزمية ترتيب تعتمد على المقارنة فقط تحتاج على الأقل قرابة n log n مقارنة في أسوأ حالة." />، وهو يعني أن الدمج والسريع (والكومة، في الصفحة العاشرة) هي **أفضل ما يمكن** بالمقارنات.

## كسر الحاجز: الترتيب بالعدّ

الحد السابق للخوارزميات التي **تقارن** فقط. لكن إذا كانت القيم أعداداً صغيرة معروفة المدى (مثل علامات من 0 إلى 10)، فلا داعي للمقارنة أصلاً:

<CountingLab />

<Tabs syncKey="algo-lang">
<TabItem label="Python">

```python
def counting_sort(a, max_value):
    count = [0] * (max_value + 1)
    for x in a:                       # one pass: count each value
        count[x] += 1
    out = []
    for value, c in enumerate(count): # one pass over the boxes
        out.extend([value] * c)
    return out

print(counting_sort([3, 7, 5, 3, 9, 10, 7, 7, 5, 8], 10))
```

</TabItem>
<TabItem label="C++">

```cpp
vector<int> countingSort(const vector<int>& a, int maxValue) {
    vector<int> count(maxValue + 1, 0), out;
    for (int x : a) count[x]++;
    for (int v = 0; v <= maxValue; v++)
        out.insert(out.end(), count[v], v);
    return out;
}
```

## الجدول الكامل

| | **الدمج** | **السريع** | **بالعدّ** |
| --- | --- | --- | --- |
| أفضل حالة | $O(n \log n)$ | $O(n \log n)$ | $O(n + k)$ |
| المتوسط | $O(n \log n)$ | $O(n \log n)$ | $O(n + k)$ |
| أسوأ حالة | $O(n \log n)$ | $O(n^2)$ | $O(n + k)$ |
| ذاكرة إضافية | $O(n)$ | $O(\log n)$ | $O(n + k)$ |
| ثابت؟ | نعم | لا | نعم (بالطريقة الكاملة) |
| يقارن؟ | نعم | نعم | لا |
| متى؟ | تحتاج ضماناً أو ثباتاً، أو بيانات أكبر من الذاكرة | الأسرع عملياً في الذاكرة | أعداد صحيحة بمدى صغير |

<Aside type="note" title="ماذا تستخدم اللغات فعلاً؟">
- **Python** (`sorted`): ‏<Term t="Timsort" en="Timsort" def="خوارزمية ترتيب هجينة من الدمج والإدراج، تستفيد من الأجزاء المرتبة أصلاً في البيانات الحقيقية." />، أي دمج ذكي يستفيد من الأجزاء المرتبة أصلاً، مع الإدراج للأجزاء الصغيرة. ثابت دائماً.
- **C++** (`std::sort`): ‏<Term t="Introsort" en="Introspective Sort" def="خوارزمية ترتيب هجينة تبدأ بالترتيب السريع، فإذا تعمّقت العودية أكثر من اللازم تتحول إلى ترتيب الكومة، وتستخدم الإدراج للأجزاء الصغيرة." />: يبدأ سريعاً، فإذا لاحظ أن العودية تعمّقت كثيراً (علامة أسوأ حالة) يتحول إلى ترتيب الكومة، فيضمن $O(n \log n)$.

الدرس: الخوارزميات الحقيقية **تجمع** أفضل ما في عدة خوارزميات.
</Aside>

## الخلاصة

- **فرّق تسد**: قسّم، وحلّ عودياً، واجمع.
- **الدمج**: يقسم بسهولة ويدمج بذكاء. $O(n \log n)$ مضمون، وثابت، لكنه يحتاج ذاكرة $O(n)$.
- **السريع**: يقسم حول محور، فيصبح المحور في مكانه النهائي. الأسرع عملياً، لكن أسوأ حالته $O(n^2)$، ونتجنّبها **بالمحور العشوائي**.
- لا يوجد ترتيب **بالمقارنة** أسرع من $n \log n$.
- **الترتيب بالعدّ** يكسر الحاجز للأعداد ذات المدى الصغير: $O(n + k)$.
- اللغات تستخدم خوارزميات **هجينة**: Timsort في Python، و Introsort في C++.

## أسئلة المراجعة

<details class="answer">
<summary>ادمج القائمتين المرتبتين [2، 6، 9] و [1، 6، 7، 12]، وعُدّ المقارنات.</summary>

2 و 1: نأخذ 1. ثم 2 و 6: نأخذ 2. ثم 6 و 6: نأخذ 6 من اليسار (للثبات). ثم 9 و 6: نأخذ 6. ثم 9 و 7: نأخذ 7. ثم 9 و 12: نأخذ 9. انتهى اليسار، فنضيف 12. النتيجة [1، 2، 6، 6، 7، 9، 12] بـ 6 مقارنات.
</details>

<details class="answer">
<summary>طبّق خطوة تقسيم واحدة من الترتيب السريع على [7، 2، 9، 4، 5] والمحور الأخير (5).</summary>

نمرّ من اليسار: 7 ليس أصغر من 5، و 2 أصغر فننقله إلى البداية ← [2، 7، 9، 4، 5]، و 9 ليس أصغر، و 4 أصغر فننقله ← [2، 4، 9، 7، 5]. ثم نضع المحور بعد منطقة الأصغر ← [2، 4، 5، 7، 9]. المحور 5 في مكانه النهائي، ونرتّب [2، 4] و [7، 9].
</details>

<details class="answer">
<summary>لماذا أسوأ حالة الترتيب السريع O(n²)، ومتى تحدث؟</summary>

عندما يكون المحور في كل مرة أكبر أو أصغر عنصر، فيصغر الجزء بعنصر واحد فقط بدل أن ينقسم إلى نصفين. فالمقارنات (n − 1) + (n − 2) + ... + 1 = n(n − 1)/2. وتحدث مثلاً مع المحور الأول أو الأخير وقائمة مرتبة.
</details>

<details class="answer">
<summary>لماذا لا يمكن لترتيب بالمقارنة أن يكون أسرع من n log n؟</summary>

لأن لـ n عنصر n! ترتيباً ممكناً، وكل مقارنة تقسم الاحتمالات إلى نصفين على الأكثر. فنحتاج على الأقل log₂(n!) مقارنة لنميّز الترتيب الصحيح، و log₂(n!) يساوي تقريباً n log₂ n.
</details>

<details class="answer">
<summary>متى لا يصلح الترتيب بالعدّ؟</summary>

عندما يكون مدى القيم كبيراً جداً مقارنة بعدد العناصر (مثل 10 أعداد بين 0 ومليار)، أو عندما لا تكون القيم أعداداً صحيحة (مثل أسماء أو أعداد عشرية)، لأننا نحتاج صندوقاً لكل قيمة ممكنة.
</details>
